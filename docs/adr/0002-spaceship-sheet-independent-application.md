# Spaceship sheet is an independent ApplicationV2 class, not a subclass of daggerheart's exposed sheet API

Status: accepted

Resolves the open spike from [#4](https://github.com/theholocoder/daggerheart-scifi-content/issues/4): whether `game.system.api.applications.sheets.api` safely exposes `DHApplicationMixin`/`DHBaseActorSheet` for cross-module extension.

## Finding

`game.system.api.applications.sheets.api.{DHApplicationMixin, DHBaseActorSheet}` are genuinely exported (`daggerheart/module/applications/sheets/api/_modules.mjs`) and nothing prevents importing them from another module. But both are unsafe to subclass for a foreign, module-registered Actor subtype:

- `DHApplicationMixin#_renderFrame` (called on every render) unconditionally reads `this.document.system.metadata.hasAttribution`.
- `DHBaseActorSheet#_prepareContext`/`#_configureRenderParts` unconditionally read `system.metadata.hasInventory`, `system.metadata.hasLimitedView`, and `system.metadata.settingSheet`.
- `metadata` is an undocumented, unversioned contract internal to daggerheart's own actor DataModels (`character`, `adversary`, `npc`, `environment`, `companion`). It is not part of any published extension API, so subclassing either class would force our Spaceship DataModel to shadow that private shape and would silently break on any daggerheart internal refactor.
- `fvtt-types` (our only type source, `tsconfig.json`) has no knowledge of `game.system.api` at all — every access would need `any`/unsafe casts, defeating `strict`/`noImplicitAny`.

## Decision

Build the Spaceship sheet as a fully independent class: `foundry.applications.api.HandlebarsApplicationMixin(foundry.applications.sheets.ActorSheetV2)`, with our own `PARTS`/`TABS`, our own Handlebars templates (`templates/`, module-namespaced), and our own CSS. No import from `game.system.api`. This keeps the sheet fully typed under `fvtt-types` and immune to daggerheart internal refactors — the only contract we depend on is core Foundry's ApplicationV2/DocumentSheetV2 API.

This decision applies to all future Spaceship-sheet work (stations, crew assignments, weapon mounts, ship level-up — [#5](https://github.com/theholocoder/daggerheart-scifi-content/issues/5)-[#9](https://github.com/theholocoder/daggerheart-scifi-content/issues/9)): keep extending our own independent base sheet class rather than reaching into `game.system.api.applications.sheets.api`.

Reading daggerheart's system-registered `game.settings` (e.g. the resource-pips appearance setting) or reusing its `armor`/`weapon` Item types on the ship Actor, as already decided in [[0001-spaceship-actor-subtype]], stays fine — that's public/system-scoped state, not a private sheet-class contract.

## Addendum: `system.metadata` and `system.getRollData()` are unavoidable, just not from the sheet

Testing surfaced that daggerheart's `Actor`/`Token` **document** classes read a small, undocumented contract off `system` unconditionally — `CONFIG.Actor.documentClass`/`CONFIG.Token.objectClass` are world-global, not overridable per sub-type, so they run for every Actor in the world regardless of which module registered its type:

- `DhpActor#_preCreate` reads `this.system.metadata.usesSize` on every Actor creation.
- `documents/token.mjs` and `documents/tokenManager.mjs` read `actor.system.metadata.usesSize` on token creation/placement.
- `applications/sidebar/tabs/actorDirectory.mjs` reads `actor.system.metadata.usesSize` on every render of the Actors sidebar list.
- `DhpActor#getRollData` unconditionally calls `this.system.getRollData()` — itself called from core Foundry's `applyActiveEffects` during every data-preparation pass, i.e. on every Actor create/update/render.

Without these, creating a Spaceship actor throws (`this.system.metadata is undefined`, then `this.system.getRollData is not a function`) and, worse, once one exists it breaks the whole Actors sidebar. This isn't a sheet-reuse question, so it doesn't reverse the Decision above: `SpaceshipData` (`src/module/data/actors/spaceship-data.ts`) defines its own `metadata` static/instance getter (matching the shape of daggerheart's own `BaseDataActor.metadata`, `module/data/actor/base.mjs`, every flag at its safe/inert default) and its own minimal `getRollData()` (mirroring `BaseDataActor.getRollData`'s default). Future Spaceship DataModel work should keep both in sync if new unconditional `system.*` reads are found in daggerheart's document-level code (as opposed to its sheet code, which we still don't touch).

[#6](https://github.com/theholocoder/daggerheart-scifi-content/issues/6) (Inventory tab) surfaced the same category of gap one level down: `Item`'s own `createDocuments` override (`build/daggerheart.js`, not sheet code, runs for `Item.createDocuments`/`createEmbeddedDocuments` on *any* actor) unconditionally calls `actor.system.isItemValid(source)` per dropped/created Item to decide whether to accept it. Without an `isItemValid` method, creating or dropping any Item on a Spaceship throws (`actor.system.isItemValid is not a function`). `SpaceshipData#isItemValid` mirrors `BaseDataActor#isItemValid`'s default body exactly (`this.metadata.hasInventory && ['weapon','armor','consumable','loot'].includes(source.type)`), which also means `metadata.hasInventory` had to flip from its previous safe/inert `false` to `true` - genuinely accurate now that the ship has an Inventory tab, not an addendum-only change.

`getRollData()` needed a second field once item actions could actually roll dice (`src/module/compat/character-only-patches.ts`'s `rollClass` patch, see the addendum below): `DualityRoll`'s own dice-construction code reads `this.data.rules.dualityRoll?.defaultHopeDice` - `.dualityRoll` itself is optional-chained, but `this.data.rules` isn't, so an actor whose `getRollData()` omits `rules` entirely throws `can't access property "dualityRoll", this.data.rules is undefined`. Fixed by returning `rules: {}` - every field daggerheart reads off `rules.dualityRoll` is itself optional-chained with a sensible fallback (12-sided Hope/Fear dice, etc.), so an empty object is enough; no need to replicate `character`'s actual house-rule schema.

## Addendum: visual parity is fine via `daggerheart`/`dh-style` CSS marker classes and copied CSS values, not via reused templates/sheet code

[#5](https://github.com/theholocoder/daggerheart-scifi-content/issues/5) asked the Spaceship sheet to visually match `daggerheart`'s own character sheet (gold window border, dark backdrop, trait/pip styling), not just be independent-but-plain. Two things from `daggerheart`'s stylesheet (`styles/daggerheart.css`) are safe to lean on without reversing the Decision above:

- `classes: ['daggerheart', 'dh-style', ...]` on our `DEFAULT_OPTIONS`: `daggerheart.css` themes any element carrying these two classes (window border/background via a `--color-border`/`--color-text-emphatic` override inside an `@scope (.theme-light, .theme-dark) to (.themed) { .dh-style ... }` block, plus generic `.application.sheet.dh-style`/`.application.daggerheart` rules) regardless of Foundry actor type. The stylesheet's own comment marks these `--dh-*` tokens as "implicitly system styles and are not namespaced" for exactly this kind of reuse. This is a CSS marker class, not a JS import - it doesn't touch `game.system.api` or subclass anything.
- Component-level CSS (trait box, Hope pip row, HP/Stress pip bar) is **copied by value** into this module's own `src/styles/main.scss`, scoped under our own `.daggerheart-scifi-content.spaceship-sheet` root, using the same class names as `daggerheart`'s markup (`character-traits`/`trait`/`trait-name`/`tier-mark`/`trait-value-area`, `hope-section`/`hope-value`) so a maintainer can compare the two side by side. This is not the same risk as importing `DHApplicationMixin`/`DHBaseActorSheet`: it's a one-time visual snapshot (colors, sizes, the trait badge SVG), not a live code dependency - `daggerheart` changing its CSS later doesn't break ours, it just drifts out of visual sync, which is an acceptable/expected maintenance cost for matching a third party's evolving look. The exception is `.slot-bar`/`.slot`/`.slot-value`/`.slot-label` (Hope/HP/Stress pip bars) and `.status-bar .status-value`/`.status-label`, which `daggerheart.css` defines fully unscoped (no `.character`/`.dh-style` prefix) - those apply to our markup for free with no CSS of our own, same reasoning as the marker classes above.

## Addendum: full-layout parity landed in [#13](https://github.com/theholocoder/daggerheart-scifi-content/issues/13) - match the official character sheet's footprint and PARTS structure, not a scaled-down copy

An earlier draft of the sheet used a single `header` PART and a narrower ad hoc sidebar (180px, later 220px) sized to fit only what had been built so far. [#13](https://github.com/theholocoder/daggerheart-scifi-content/issues/13) replaced that with the same structure `daggerheart`'s own character sheet uses, matched exactly rather than approximated:

- Window `850x800`, `275px` fixed sidebar column (`character-header-sheet`'s own dimensions, copied by value per the addendum above).
- `PARTS`: `sidebar` / `header` / one part per tab (`features`, `inventory`, `stations`, `effects`), on a `window-content` CSS grid - sidebar spans both rows of column 1, header sits in row 1 of column 2, the active `.tab` fills row 2 of column 2. This mirrors `daggerheart`'s own `.character .window-content` grid rules (still copied by value, not imported).
- The system styles `.sheet.dh-style .window-header` as a transparent `position: absolute` overlay (so its close/context-menu buttons float over the sheet body); the header PART pads its top by `--header-height` to clear it, a detail easy to lose if the header is rebuilt from scratch.
- A "Configure Spaceship" settings dialog (`src/module/applications/settings/spaceship-settings.ts`) is a second, independent `ActorSheetV2` instance on the same actor document (not registered via `DocumentSheetConfig`, instantiated directly from a sheet action), `submitOnChange`, styled via the `daggerheart dh-style dialog` marker classes - the pattern to reuse for any future per-actor settings dialog on this sheet, mirroring `daggerheart`'s own `DHCharacterSettings`/`DHBaseActorSettings` split.

Later tickets ([#6](https://github.com/theholocoder/daggerheart-scifi-content/issues/6)-[#12](https://github.com/theholocoder/daggerheart-scifi-content/issues/12)) should treat this footprint and PARTS layout as the baseline to build into (replacing `templates/actors/spaceship/tab-placeholder.hbs` per tab), not something to re-derive or shrink back down.

## Addendum: [#6](https://github.com/theholocoder/daggerheart-scifi-content/issues/6) extends "copied by value" from CSS to item-row markup, still not to templates/sheet code

The Inventory tab's item rows (`templates/actors/spaceship/inventory.hbs`) copy `daggerheart`'s own `fieldset.glassy`/`legend`/`items-list`/`inventory-item`/`item-main`/`inventory-item-header`/`img-portait`/`item-label`/`item-tags`/`item-resource`/`controls` class names and DOM shape by value from `templates/sheets/global/partials/inventory-item-V2.hbs` and `inventory-fieldset-items-V2.hbs` - not by `{{> "systems/daggerheart/..."}}`-including those files (a live template dependency the "Decision" above rules out), but by hand-writing equivalent markup with the same classes. `daggerheart.css` themes essentially all of it unscoped under `.application.daggerheart.dh-style` (`.inventory-item`, `.items-list`, `.item-tags .tag`, `fieldset.glassy legend`, etc. carry no `.character`/actor-type prefix - confirmed by grepping `styles/daggerheart.css`), so this is the same "copy by value" reasoning as the addendum above, just extended from CSS rules to the HTML shape those rules target. The one exception is `.items-section` (the fieldsets' flex/scroll container), which *is* scoped to `.character`/`.party` there - its layout is copied by value into our own SCSS instead of relied on for free.

Behavior stays our own: `data-action="createItem"/"editItem"/"deleteItem"/"toggleEquipItem"/"toggleExtended"` are wired to `SpaceshipActorSheet`'s own action handlers, not the system's sheet JS. Two pieces of live `daggerheart` behavior are reused directly, both `Item`-document-level (not sheet code, same "public/system-scoped state" category as reusing the `armor`/`weapon` Item types per the Decision above):

- `item._getTags()` produces each item's tag chips ("Finesse"/"One-Handed"/"Base Score: 3"...). Called once per item in `#buildInventoryContext` (`spaceship-actor-sheet.ts`), not from the template: Handlebars only binds a resolved function's `this` correctly when it's a *direct* property of the current context (`item-tags.hbs` relies on exactly that, invoking `_getTags` as a bare path with `item` as the partial's own context) - a nested path like `item._getTags` in our template would call it with the wrong `this` and break every tag reading `this.attack`/`this.armor`/etc.
- `item.hasDescription`/`item.system.getEnrichedDescription()` + core's `TextEditor.enrichHTML` drive the expand-on-click description, filled into `.inventory-description` from `#enrichInventoryDescriptions` (called from `_onRender`, since Handlebars can't `await`) - the same content daggerheart's own `#prepareInventoryDescription` injects, just triggered by our own `toggleExtended` handler instead of theirs.

Item-level `system.actions` ("Use" buttons below a row, e.g. a Medpack's Healing action, and click-portrait-to-roll) needed a third approach, escalating past both: daggerheart hard-codes several `character`-only gates around item actions - `BaseDataItem#actionsList`/`DHWeapon#actionsList` (comment: `// No actions on non-characters`) and `DHItem#usable` (drives the portrait's click-to-roll vs. click-to-edit, and its hover roll-icon) all return an empty/falsy result for any non-`character` actor. Not a "safe/inert default" gap like `isItemValid`/`metadata` were, and not something copying markup/reusing an Item-level getter as-is (the pattern above) can work around either, since the getter itself is what's gated. First attempt left the feature out entirely (its "Use" dialog crashed on `undefined.parent` trying to resolve costs for an action it couldn't find).

Reinstated via `src/module/compat/character-only-patches.ts`: `lib-wrapper` patches, registered at `init`, wrapping the relevant getters to also treat a Spaceship actor as valid - every other actor type's behavior is untouched (each wrapper only intercepts for our own actor type, calling the original getter otherwise). Two things worth recording as pitfalls hit along the way:

- `actionsList` needed **one registration per item-type class** (`armor`/`consumable`/`loot`/`weapon`), not one shared registration against whichever prototype happened to be convenient. `armor`/`consumable`/`loot` all inherit the same `BaseDataItem#actionsList` rather than defining their own, and registering against only one of their `.prototype`s (`loot`) did *not* also fix the others in testing - a Medpack (`consumable`) still crashed. `libWrapper` shadows the getter on the specific prototype named by the target string; it doesn't propagate to sibling classes that merely share an ancestor.
- `usable` is a single getter on the Item *document* class itself (`CONFIG.Item.documentClass`, shared by every item type) rather than the per-type `system` DataModel `actionsList` lives on - one registration covers all four types.

`lib-wrapper` is a required module dependency (`src/module.json`) specifically for this; without it active, the patches no-op defensively rather than crashing at load.

This is a genuinely different category of risk from the CSS-by-value/Item-type-reuse addenda above - not reading public/system-scoped state or copying markup, but monkey-patching daggerheart's own internal methods. Chosen deliberately (over: leaving the feature off; making the button open the item sheet instead of rolling; reimplementing simple actions ourselves) specifically because it's the only option that gets the *real* daggerheart roll/cost/chat pipeline working identically to a character, and `lib-wrapper`'s chaining means it coexists safely with any other module patching the same getters. Confirmed working for non-roll actions (Healing, etc.).

Two more gates showed up once roll-type actions were actually tested, and the first fix (patching `rollTrait` alone) turned out to be treating a symptom, not the cause:

- `DhpActor#rollClass` (`CONFIG.Actor.documentClass`, i.e. *any* actor) is what actually picks the dice: `CONFIG.Dice.daggerheart[['character','companion'].includes(this.type) ? 'DualityRoll' : 'D20Roll']`. A ship's weapon Attack opened a real, working roll dialog - just the adversary-style flat-d20 one, because `this.type` is never `'character'`/`'companion'` for a ship. This is the actual fix for "wrong dice"; it's reachable at a stable path, so it's a normal `libWrapper` registration like `actionsList`/`usable`.
- `DHActionRollData#rollTrait` (`this.parent.actor.type !== 'character'` -> `null`) is a real, separate gate too - once `rollClass` is fixed and a duality roll is actually being built, an unpatched `rollTrait` still picks no trait modifier at all. `DHActionRollData` isn't reachable at any stable global path, unlike the `CONFIG.Item.dataModels.*`/`CONFIG.Item.documentClass`/`CONFIG.Actor.documentClass` paths the other three patches target - only reachable at runtime via `new (game.system.api.fields.ActionFields.RollField)().model` (daggerheart's own public API surface for its Action field classes, `.model` being where Foundry's `EmbeddedDataField` base class stores the DataModel a field wraps). `libWrapper.register`'s string-target resolution can't express that lookup, so this one is a plain `Object.defineProperty` monkey-patch instead - same "only take over for our own actor type" shape, just applied by hand.

The lesson: a `character`-only check surfacing as "wrong behavior" rather than a crash (unlike `isItemValid`/`actionsList`/`usable`, which all threw) is easy to misdiagnose from source-reading alone - `rollTrait` looked like the obvious culprit for "wrong dice" and wasn't; `rollClass` was. Confirming a fix like this needs an actual roll attempt in a running world, not just tracing the call chain from documentation.

## Addendum: Inventory row controls match the character sheet's own *default* set - equip/Send to Chat/kebab menu, not standalone edit/delete icons

An early version of `inventory.hbs` gave each row a fixed `equip` + `edit` + `delete` control set - plausible-looking, but not what daggerheart's own inventory list actually renders by default. Its `inventory-item-V2.hbs` only shows standalone edit/delete icons when a caller explicitly passes `hideContextMenu: true`; the character sheet's own `character/inventory.hbs` never does, so its real default is: equip toggle, "Send to Chat" (`toChat`, an Item-level method - `item.toChat(item.uuid)`, not sheet code), then a kebab button (`triggerContextMenu`) opening a context menu with Edit/Delete. `toChat` is reused directly; the context menu is built with core's own `ContextMenu` class (`#bindItemContextMenu`, cached on the instance like `ActorSheetV2`'s own `_dragDrop` - `ContextMenu`'s constructor binds a listener to its container, and that container (`this.element`) persists across re-renders, so constructing a new one on every render would accumulate listeners) rather than daggerheart's own `triggerContextMenu` handler, which is sheet code.

## Addendum: check for an existing daggerheart color rule before overriding one

A recurring mistake across #6's several rounds: item text/tags/control-icons/quantity-input were each, at different points, force-colored white in `main.scss` on the assumption that daggerheart's CSS didn't already handle them. `.item-buttons button` was one such wrong override, confirmed and reverted - it already sets `color: var(--dh-button-color-text)` in `daggerheart.css`, and its non-first-child variant sets a *dark* text color against a light button background, so the flat-white override made that text unreadable, the opposite of the intended fix. `.item-name`/`.inventory-description`/`.controls a` genuinely have no color rule of their own anywhere in `daggerheart.css`, so they fall back to whatever `color` is ambient - the official character sheet inherits a light near-white core token (`--color-text-primary`) there, ours was inheriting this sheet's own root `color: var(--color-text-emphatic)` (set for the header/sidebar, gold/amber) instead; fixed by resetting those three specifically to `--color-text-primary`, not a hardcoded white. Same story for `.inventory-item-quantity`: `daggerheart.css`'s unscoped `.dh-style input[type='number']` rule already sets a correctly-themed `color`/`border` (via `--dh-input-color-text`/`--dh-input-color-border`) - this module's own pre-existing generic `input { border: 1px solid transparent; color: inherit; }` rule (predating #6, for the header/trait/level inputs) was winning on specificity and blanking it out; fixed with a `:not(.inventory-item-quantity)` exclusion on that rule instead of yet another hardcoded-white override.

`.item-tags .tag` is the one exception that didn't fit this pattern cleanly: it *does* have its own `color: var(--color-light-2)` rule in `daggerheart.css`, and tracing selector specificity says that rule should already win over this sheet's root color - but removing the override on that theory produced yellow tags live, twice, confirmed by direct user testing. Reinstated on the empirical report rather than the specificity trace; the trace and the live result disagree and that gap is unresolved (something about how `--color-light-2` actually resolves in this rendering context isn't accounted for above) - worth a real devtools computed-style check before touching it again, not another theory from reading the stylesheet.

The standing rule going forward: before adding a color/style override for anything carrying a `daggerheart`-reused class, grep `styles/daggerheart.css` for that class first - most css visual gaps on this sheet turn out to be *this module's own* CSS shadowing something daggerheart already provides for free, not an actual gap in daggerheart's stylesheet. But a specificity trace from source is a hypothesis, not a substitute for checking the actual rendered result - `.item-tags .tag` is the counter-example.

## Addendum: `ActorSheetV2` (core, not daggerheart) already wires up drag-drop - don't build a second one

An earlier version of the Inventory tab's drag-drop bound its own `dragover`/`drop` listeners directly onto `.spaceship-inventory` from `_onRender`. That duplicated every dropped item: `foundry.applications.sheets.ActorSheetV2` (core Foundry, the class `SpaceshipActorSheet` actually extends, per the Decision above - not daggerheart's `DHBaseActorSheet`) already has its own `_dragDrop` (a `DragDrop` controller, `dropSelector: null` so it catches a drop anywhere on `this.element`) which its *own* `_onRender` binds on every render, routing an Item drop to `this._onDropItem(event, item)`. Both listeners fired on the same physical drop event - the built-in one (via event bubbling from wherever inside `this.element` the drop landed) and the hand-rolled one - each independently calling `createEmbeddedDocuments`.

Fixed by overriding `_onDropItem` instead of adding a competing listener: reject non-`INVENTORY_ITEM_TYPES` drops with a warning, otherwise call up the prototype chain (not `super._onDropItem` - fvtt-types doesn't declare it, the same gap `_prepareContext`/`_preparePartContext` already work around) to let the base class do the actual embedding - it already handles same-actor reorder, compendium source items, and ownership correctly, none of which the hand-rolled version did. `maxWeaponMounts` enforcement moved to run *after* that call, unequipping the newly-created copy if it landed over cap, since the base method offers no hook to adjust the create data beforehand.

This is a caution for future Spaceship-sheet work generally: `ActorSheetV2` (core) provides more built-in behavior than the header/traits/resources code written so far uses (this drag-drop wiring, `_onDropActor`/`_onDropFolder`/`_onDropActiveEffect`, `_getHeaderControls`, etc.) - check for an existing hook before hand-rolling a DOM listener for something a sheet already gets from its base class.

## Addendum: [#7](https://github.com/theholocoder/daggerheart-scifi-content/issues/7) - item lists moved into module-owned shared partials, mirroring daggerheart's own partial split

`daggerheart`'s character sheet renders its **Features** tab through the *exact same* pair of partials as its Inventory tab: `templates/sheets/actors/character/features.hbs` -> `daggerheart.inventory-items` (`inventory-fieldset-items-V2.hbs`) -> `daggerheart.inventory-item` (`inventory-item-V2.hbs`), just with `type='feature'` and no equip/quantity controls. #6 had copied that row markup by value but *inline*, as a `{{#*inline "row"}}` local partial inside `inventory.hbs`, which a second tab can't reach.

#7 therefore split it the same way the system does, rather than copying the row markup a second time:

- `templates/actors/spaceship/partials/inventory-item.hbs` (one row) and `partials/inventory-fieldset-items.hbs` (fieldset/legend/create-button/list), registered as `dhscifi.inventory-item`/`dhscifi.inventory-items` from `src/main.ts` via core's `foundry.applications.handlebars.loadTemplates`. Module-owned *copies* named after daggerheart's pair - deliberately **not** `loadTemplates`-ing the system's actual `.hbs` files, which would be exactly the live template dependency the Decision above rules out.
- `inventory.hbs` (#6) and `features.hbs` (#7) are now both thin: a tab `<section>` plus one partial call per section. Every visual/behavioral detail #6 established (portrait roll-vs-edit, tag chips, expandable enriched description, equip toggle, Send to Chat, kebab context menu, `.item-buttons` actions) applies to feature rows for free.
- Features is a *single* section, matching daggerheart's own generic `templates/sheets/global/tabs/tab-features.hbs` for non-character actors. The character sheet's multi-section split comes from `system.sheetLists` (class/subclass/ancestry/community granters), concepts a ship doesn't have per `CONTEXT.md`.
- `.features-sections` is the character sheet's own container class for that tab; `daggerheart.css` scopes that rule to `.character`, so its layout is copied by value into `main.scss` - same exception `.items-section` already was.

Three sheet-wide consequences worth keeping in mind for the remaining tabs (#8-#12), since they'll reuse the same partials:

- The post-render DOM wiring (`#bindItemContextMenu`, `#bindQuantityInputs`, `#enrichInventoryDescriptions`) was scoped to `.spaceship-inventory`; it now matches `.inventory-item` sheet-wide. A new tab rendering rows through these partials gets all three automatically.
- The `.inventory-item` text-color overrides moved out of `.spaceship-inventory` for the same reason.
- The accepted-Item-type lists moved to `src/module/constants.ts` (`INVENTORY_ITEM_TYPES`, `FEATURE_ITEM_TYPE`, `SPACESHIP_ITEM_TYPES`), imported by **both** halves of the same accept/reject rule: `SpaceshipActorSheet` (create/drop gate, rejects with our own message) and `SpaceshipData#isItemValid` (the document-level gate daggerheart's `Item.createDocuments` override consults). They previously each spelled out their own literal, which had to be kept in sync editorially; now widening is one edit. A type the sheet allows but `isItemValid` rejects would fail with the system's generic warning instead of ours; a type `isItemValid` allows but the sheet doesn't simply can't be dropped. The user-facing `DHSCIFI.Spaceship.Inventory.InvalidItemType` string in `lang/*.json` enumerates the same list in prose and is the one place still updated by hand.
- `isItemValid`'s `feature` branch deliberately sits *outside* the `metadata.hasInventory` gate (`(hasInventory && isInventoryType) || type === 'feature'`), mirroring `super.isItemValid(source) || source.type === 'feature'` in daggerheart's own feature-bearing DataModels: a feature isn't inventory, so it shouldn't hang off an inventory flag.
- **`@root.editable` now gates every mutating affordance** in the shared partials - the "+" create button, the equip toggle, the kebab (Edit/Delete) menu, the quantity input, the `.item-buttons` action buttons, and the portrait's roll-vs-open behavior. This matches the character sheet, which gates the same set (`canCreate=@root.editable`, `showActions=@root.editable` from *both* its tabs, `{{#if @root.editable}}` around its equip toggles); "Send to Chat" stays ungated, being read-only. Because `showActions` is uniformly `editable` on the character sheet, this module collapses it into the precomputed `usable` flag in `#toEntry` rather than threading a second parameter through the partials. Before this, an observer/limited user saw create and Delete affordances that would only fail server-side.
- `isGlassy` is a partial parameter rather than a hardcoded class, because the character sheet's two tabs genuinely differ: its Inventory tab passes `isGlassy=true`, its Features tab does not.
- Subexpression helpers (`(and ...)`, `(or ...)`, `(eq ...)`) are avoided in these partials in favour of nested plain `{{#if}}`s: those come from daggerheart's own helper registrations, and this module registers only its own (`dhscifiResourceBoxes`), per the Decision above.

**Known gap, deliberately not closed here:** daggerheart's `inventory-item-V2.hbs` puts `draggable="true"` on `.img-portait` and `.item-label`, so a character's items can be dragged out to another sheet or the hotbar. Our rows omit it (inherited from #6, not introduced by #7). Adding the attribute alone is not enough and was left out rather than guessed at: it needs a matching `dragSelector` in the sheet's `dragDrop` options plus an `_onDragStart` that writes the right drag payload, and core `ActorSheetV2`'s default `dragSelector` was not confirmed from source in this environment (only the Foundry *data* directory is available locally, not the application bundle). A bare `draggable` with no payload wiring produces a native image-drag that silently does nothing useful - worse than no affordance. Worth its own ticket, covering both tabs.

No new `character`-only gate needed patching for this tab: `BaseDataItem#actionsList`'s gate is conditioned on `metadata.isInventoryItem`, which `DHFeature` leaves false, so a feature's actions already resolve on any actor - the `usable` patch from #6 (Item-document-level, all types) is what makes its portrait roll.

## Addendum: [#8](https://github.com/theholocoder/daggerheart-scifi-content/issues/8) (Stations) — the item-row *skeleton* is reusable beyond items, and crew references are core fields, not daggerheart's

The Stations tab holds Actor references, not embedded Items, yet it still renders through daggerheart's own list markup: one `fieldset.glassy.drop-section` + `legend` per station (the shape `partials/inventory-fieldset-items.hbs` builds) wrapping a `ul.items-list` of `li.inventory-item` rows with the same `item-main`/`inventory-item-header`/`img-portait`/`item-label`/`item-name`/`controls` skeleton. This is the same copy-by-value reuse #6/#7 established, just applied to a non-Item payload.

Worth being precise about *which* of those classes actually earn their keep, because #6/#7's addenda were looser than the stylesheet supports. The ones carrying the look genuinely are unscoped under `.application.daggerheart.dh-style`: `fieldset.glassy` and its `legend` (`daggerheart.css`'s `.dh-style fieldset.glassy`), `.inventory-item`, `.item-main`, `.img-portait`, `.item-label`. Two are **inert** and kept only for structural parity with the system's own markup: `.drop-section` has exactly one rule, scoped to `.class .tab.settings .fieldsets-section`, and `.items-list`'s unscoped-looking rules are all under the `.limited` sheet containers. Both are already carried by `partials/inventory-fieldset-items.hbs` for the same reason — the system itself puts `.drop-section` on `inventory-fieldset-items-V2.hbs`, where it is equally inert — so this isn't a reason to drop them, just a correction to the blanket "all of these are themed for free" claim in the #6 addendum above.

It is deliberately *not* the `dhscifi.inventory-item` partial. That partial is built around an embedded Item — `data-item-id`, tag chips, equip/quantity/chat/context-menu controls, an expandable enriched description — none of which a crew assignment (a bare UUID string with a name and a portrait) has. Sharing the class names is free; sharing the partial would mean threading half a dozen "this isn't an item" flags through it. The dividing line for later tickets: reuse the partial for embedded Items, reuse the markup skeleton for anything else.

Two smaller points:

- `templates/sheets/actors/party/party-members.hbs` is the system's only drop-an-Actor-onto-a-sheet precedent, and its behavior was mirrored (drop appends a UUID, an `X` removes with a Shift-skippable confirm, an empty list shows the dashed `.actors-dragger` hint). Its *styling* could not be reused: every `.actors-list`/`.actor-resources`/`.actors-dragger` rule in `daggerheart.css` is scoped to `.party .tab.partyMembers`. Only `.actors-dragger` and `.delete-icon`'s size were worth copying by value; the rest of the party's grid layout was dropped in favour of the item-row skeleton above, which fits this sheet's other tabs.
- `opacity` is the wrong tool for dimming a container that holds its own escape hatch. The disabled-station treatment first put `opacity: 0.5` on the fieldset with a `legend a { opacity: 1 }` "exception" for the re-enable toggle; that does nothing, because an opacity below 1 creates an opacity group and no descendant can render more opaque than its group — the only control that undoes the disabled state dimmed along with everything else. The fix dims the station's *contents* (`> .items-list`) and re-colours the legend text, leaving the toggle at full strength. Same category as the "check for an existing daggerheart color rule" addendum below: a CSS trace is a hypothesis until the rendered result agrees.
- The stored reference is core's own `foundry.data.fields.DocumentUUIDField` inside a plain `ArrayField` — **not** daggerheart's `ForeignDocumentUUIDArrayField`, which initializes to live Documents and is system-internal (same reasoning as the Decision above). Resolution happens in the sheet via `fromUuidSync`, guarded: it returns `null` for a deleted world Actor but *throws* for a compendium UUID whose pack index isn't loaded, and both are the same "Unknown" outcome the ticket asks for. This is what keeps the reference genuinely one-way (CONTEXT.md's "Crew assignment"): nothing cleans up a dangling entry, and disabling a station leaves its `crew` array intact so re-enabling restores it.

Two behaviours are deliberately borrowed from `party-members.hbs` rather than derived from #8's own text, and are flagged here so a later ticket doesn't read them as accidental: a station **rejects a duplicate assignment** of the same Actor with a warning (the party sheet's own `duplicateCharacter` rule), and a resolved crew portrait **opens that Actor's sheet** (the party sheet's `openDocument` affordance). Neither is asked for by #8; both follow from its "reuse the official implementation" framing, and a station holding the same Actor twice has no meaning under CONTEXT.md's "Crew assignment".

`_onDropActor`'s return value is part of core's contract, not decoration: `client/applications/sheets/actor-sheet.mjs` documents "an Actor … to indicate success, or a nullish value to indicate failure or no action being taken", and `_onDropDocument` propagates it to the caller. Return the dropped Actor on a successful assignment and `null` on every rejection — an early version returned `null` unconditionally, reporting failure on every successful drop.

**The environment gap recorded in #7's "Known gap" above no longer holds.** The Foundry application bundle *is* readable locally at `~/jdr/FoundryVTT/resources/app/` (`client/applications/sheets/actor-sheet.mjs` etc.), not just the data directory. #8 used it to confirm from source that core `ActorSheetV2#_onDrop` → `#_onDropDocument` dispatches an Actor drop to `_onDropActor(event, actor)` with the resolved Document, that its default implementation returns `null` (so there is nothing to delegate to, unlike `_onDropItem`), and that `_canDragDrop` already gates drops on `isEditable`. The `draggable`/`_onDragStart` ticket that gap describes is now answerable from source rather than by guessing.

## Addendum: [#9](https://github.com/theholocoder/daggerheart-scifi-content/issues/9) (Effects) — an ActiveEffect is a row like any other, so the row partial and the row plumbing were generalized, not duplicated

The Effects tab is the first list on this sheet whose rows are not embedded Items. The reusable-unit question #8's addendum left open ("reuse the partial for embedded Items, reuse the markup skeleton for anything else") resolves the *other* way here, and deliberately so: daggerheart itself renders its effect rows through the very same `daggerheart.inventory-item` partial as its weapons, armor, and features, with `type='effect'` switching a handful of branches inside it. An ActiveEffect, unlike a crew assignment, really is a document with a name, a portrait, a description, a sheet, and a delete — it fits the row contract; a bare UUID string does not.

So #9 extended the existing pair rather than adding a third one:

- `partials/inventory-item.hbs` gained an `isEffect` branch, mirroring daggerheart's own `type='effect'` branches one for one: `data-type="effect"`/`data-disabled` on the `li`, and the `fa-toggle-on`/`fa-toggle-off` enable/disable control in the equip toggle's slot. Nothing else on the row needed a branch, because `DhActiveEffect` defines its own `_getTags` (an origin chip plus one per applied status), `hasDescription`, and `toChat` — an effect row lights up the same tags, description expander, and "Send to Chat" an item row does. Only `usable` is Item-only, so an effect's portrait opens its config sheet instead of rolling, which is what upstream's row does too.
- `partials/inventory-fieldset-items.hbs` gained `isEffect`/`createDisabled`, matching the `type`/`disabled` parameters its upstream counterpart uses to make the *inactive* section's "+" create an already-disabled effect.
- `templates/actors/spaceship/effects.hbs` is structurally the character sheet's own `effects.hbs`: one `.effects-sections` wrapper, two glassy fieldsets, the active/inactive split.

Three pieces of sheet plumbing had to stop being Item-specific for that to work, each of which has a direct upstream counterpart that was *already* document-generic — evidence the narrower version was the accident, not the generalization:

- **Row resolution.** `#getRowItem(actor, target)` looked its document up as `actor.items.get(dataset.itemId)`, which can only ever find an Item. It is now `#getRowDocument(target)` — `fromUuidSync` off the row's `data-item-uuid`, guarded the same way `#resolveCrewEntry` is — which is exactly daggerheart's own `getDocFromElementSync`, the single helper every one of its row actions goes through. `editItem` and the context menu's Edit/Delete then work on an effect with no further branching.
- **Description enrichment.** An ActiveEffect's description is a top-level document field, not `system.description`. The fallback chain now matches upstream's `doc.system?.description ?? doc.description` exactly.
- **The context menu.** One `ContextMenu` still covers every row on the sheet; its entries are switched on the row's `data-type` through core `ContextMenu`'s own `condition` callback. Daggerheart instead registers two menus against two selectors, but only because its base class takes a declarative `contextMenus` array — with one hand-built menu here, conditioned entries reach the same place with one binding. The Enable/Disable pair is a transcription of its `#getEffectContextOptions`.

`LooseItem` was renamed `LooseDoc` to say what it now stands in for. The one field an ActiveEffect lacks (`usable`) was already optional, so `#toEntry` builds an effect row unchanged; only `canChat` (the resolved form of upstream's `{{#if (hasProperty item "toChat")}}` guard, which this module has no helper for) and `disabled` were added.

Two things came for free and are worth recording so they aren't re-derived:

- **No `character`-only gate needed patching.** `DhpActor#allApplicableEffects` — daggerheart's override, on the world-global `CONFIG.Actor.documentClass` — only adds the `noSelfArmor`/`noTransferArmor` filters and is actor-type agnostic. `DhActiveEffect#hasDescription` likewise. This tab needed nothing added to `character-only-patches.ts`.
- **`noTransferArmor: true`** is not incidental: it is what daggerheart's own effects tab passes, so an armor item's transferred effect isn't listed as a separately togglable row alongside the Shield/threshold numbers ([#10](https://github.com/theholocoder/daggerheart-scifi-content/issues/10)) that already represent it.

With #9 every tab in `TABS` has a real template, so `templates/actors/spaceship/tab-placeholder.hbs` and its `.dhscifi-placeholder-body` styles were deleted — the tab-level use the #13 addendum above describes is finished. The unrelated `.dhscifi-placeholder` *inline* markers (Shield, thresholds, Hope) stay: those belong to [#10](https://github.com/theholocoder/daggerheart-scifi-content/issues/10)/[#11](https://github.com/theholocoder/daggerheart-scifi-content/issues/11).
